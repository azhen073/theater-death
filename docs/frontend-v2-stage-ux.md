# web-v2 舞台行动交互与响应式布局规格

本文档记录 PR A 阶段关于局内行动交互收拢与响应式布局的已定案工程规格。

## 开局身份揭示（v2.0.5-alpha）

正式玩家每局首次进入对局时显示一次舞台中央身份卡，内容来自已授权的 `private.self` 与角色目录。它只有“进入舞台”按钮，不提交命令，也不替代可反复打开的“我的身份”。公共观众、私人第二屏与复盘不自动显示。

前端以 `roomId + gameId + subjectPlayerId` 写入 `sessionStorage` 去重；显示前即占用该键，避免刷新或重连重播。本人有效行动剩余不超过 10 秒，或倒计时不可可靠计算时，直接让位行动并把本局记为已处理；弹层显示期间进入该阈值也立即关闭，不在本局补弹。

## 1. 核心交互原则

### 公开死亡视觉（2026-09-22 增补）

- 新 `deaths_announced` / `elimination_announced` 到达时，在对应座位头像周围播放红黑烟雾与碎片，最长 3.2 秒；短文字公告同步出现。每席位独立计时，连续不同批次不会互相清掉，也不会因重复快照延长。
- 已公开死亡的头像覆盖静态星芒与烟痕；依据 `public.seats[].alive` 恢复/移除。私有濒死、私人死讯不触发公共粒子或印记；死亡后可用的遗言、回归、管理权限仍完全由现有任务/能力决定。
- 同一快照里死亡后立即回归，以最终公开存活状态为准；不在已回归头像上闪现死亡标记。回归后再次出现新的公开死讯可再次播放。
- 首次加载、刷新、重连、页面隐藏/返回、换房间/局/账号/视角只建立游标基线，不重播历史。监听器挂载在房间容器，正在观看时 `playing → review` 的最后一次新死讯保留文字公告；初次打开复盘不会播放。
- “减少动画”保留静态印记和公告、不运行粒子；关闭“死亡特效”关闭粒子和大印记，保留灰度、死亡文字与公告/记录。重新开启不会补播当前旧批次。
- 粒子画布只覆盖舞台且 `pointer-events:none`，不弹确认、不改计时、不挤占公屏。每次仅一个画布，碎片总预算随舞台宽度限制为 100/220 个；DPR 上限 2，画布最长边上限 4096 像素；到期/隐藏/卸载停止动画并释放计时器。

本迭代保留舞台几何与公屏宽度；头像复用现有合图的裁切区域，素材来源见 `frontend-v2-assets.md`。上述时间与预算是工程呈现参数，不是玩法窗口。

1. **舞台全收拢**：所有 18 种行动任务、目标选择、参数调整、一次性最终提交、即时反馈与网络未决恢复全部在舞台（Stage）内部完成。
2. **废除旧外壳**：移除舞台下方独立行动面板（`.action-dock`）与屏幕底部固定行动条（`.mobile-action-bar`），消除双重提交入口。
3. **单次最终确认**：合法意图仅确认一次；无目标动作点击即确认；空守/弃票/跳过由明确的独立按钮触发，清空草稿仅重置本地选择不发请求。
4. **公屏零改动**：电脑右侧公屏位置、300px/280px 宽度规则、四标签（公屏/情报/记录/规则）与聊天发送及历史滚动行为严格保持现状。
5. **团队一次提交（v2.0.7-alpha 起为单按钮）**：支持标记存在时，编辑者一次“发布并确认”原子创建方案并确认本人；队友仍逐人同意当前版本。支持标记缺省时保留原有编辑／确认两步入口。
   - 组合流程下**只有一个动作按钮**，标签即载荷：草稿未改（＝最新方案）→「同意方案 v(n)」（发 `CONFIRM_PROPOSAL`，不新建版本）；改了且有目标 →「发布并确认方案」（`EDIT_PROPOSAL` + `confirmSelf`）；本地目标为空（含 v0 无草稿）→ 同一个按钮变「发布并确认空刀」。要发布空刀先点「清空选择」。空刀落地后仍是**合法草稿**（可与队友版本竞争，截止时按“全员确认 → 最后合法草稿 → 空刀”兜底），因此不再与方案按钮并列，避免误触覆盖队友名单。
   - **草稿目标与我的选择的颜色区分**（仅在提案窗口 `EDIT_PROPOSAL` / `CONFIRM_PROPOSAL` 内生效）：**我的选择**＝深蓝实线 `#455974` ＋「已选」角标；**当前草稿目标**（`private.proposal.targetPlayerIds`，即队友或自己已发布的版本）＝青色虚线 `#2f7d8c` ＋左侧「草稿」角标；两者命中同一座位时保留深蓝实线并加青色外环。方案面板内给出一行图例（「我的选择 / 当前草稿目标」），座位 `aria-label` 对草稿目标补「在队伍草稿中」，因此不依赖颜色单独承载信息。
      - **昼夜同一套色（v2.0.7-alpha 修正）**：三种座位态的颜色只由 `main.css` 的 `--seat-selected*` / `--seat-draft*` 变量定义，夜间不再单独覆盖「我的选择」（此前 `night-atmosphere.css` 的 `.theater-stage--night .stage-seat--selected .seat-main` 会把选中态压成淡蓝 `#9bbfff`，与日间不一致）。三条座位态规则统一带 `.theater-stage` 前缀，特异度高于 `.theater-stage--night .seat-main`（夜间座位底色 `#f5f8fd` 仍保留），因此无需夜间覆盖；夜间「不可选」态覆盖不变。
   - **目标选择＝点击切换（v2.0.7-alpha）**：点击座位即选中、再点同一座位即取消；座位角标只有「已选」，`maxTargets` 的含义是「不同目标数上限」。**界面不再提供"同一目标多刀"**（座位上的 `−` / `＋` 已移除；用户裁定：规则上不需要对单个目标双刀）。服务端与引擎仍接受重复目标载荷，只是界面不再表达——引擎、契约与既有校验未改。
   - **空目标一律说「空刀」**（v2.0.7-alpha）：`private.proposal.targetPlayerIds` 为空时，方案面板的**最新草稿行**显示「最新草稿 v{n}：空刀」、**生效行**显示「v{n} · 空刀（今晚不出刀）」；`revision === 0` 仍显示「尚无草稿」，「没有可采用的草稿」仍显示「当前无草稿（空刀）」。「空选择」只描述**本地选择**为空（`targetSummary([])` 的既有返回值），不得用来描述队伍方案。

6. **窄屏（≤680px）滚动后 HUD 收成细条**（v2.0.7-alpha）：`GameScene` 用 `scroll`/`resize`（rAF 节流）+ `matchMedia('(max-width: 680px)')` 判断；**滞回阈值**为「下滑超过 120px 收起、回到 24px 以内展开」，避免临界抖动。收起态只留「第 N 轮 · 白天/夜晚 · 第 M 阶段」＋阶段名＋倒计时＋**「更多」**按钮（实测高约 44px，原两行 123px），四个操作（我的身份 / 导航 / 第二屏 / 房间管理）移入「更多」展开的面板（`aria-expanded`、容器 `aria-label="对局操作"`；同一时刻只渲染一处，避免按钮重名）。桌面宽度（>680px）永不收起，行为与以前一致。**与引擎无关**：满血 HUD 在手机端吸附时会盖住一整排座位（滚动 900px 时 3 个座位全被盖、6 个部分被盖，chromium 与 webkit 同值），收起后第一排座位完全露出。E2E 见 `e2e/specs-v2/29-hud-compact.spec.ts`；需要点击 HUD 操作的用例统一先调 `e2e/helpers-v2/rooms.ts` 的 `revealHudActions(page)`（展开态下是空操作）。

## 2. 纯展示推导层（Presentation Layer）

- 模块：`web-v2/src/features/actions/presentation.ts`
- 纯函数 `deriveActionPresentation` 接收 `view`、`task`、`draft`、`records`、`online`、`remainingMs` 与当前 scope 的提交证据，输出结构化的 `ActionPresentation`。
- 状态集合：`editing`、`sending`、`accepted`、`changed`、`rejected`、`recovering`、`expired`、`offline`、`idle`。
- 状态隔离：按与 `CommandTracker` 一致的用户、房间、局号、成员、玩家视角和只读状态隔离草稿、回执与提交证据；scope 切换首帧即屏蔽旧数据。
- 提交依据：发送前记录当时的 snapshot requestId 与 viewVersion。快照与最新 accepted 回执冲突时只选择一份依据；顺序未知则显示同步状态，同一冲突仅自动刷新一次，并允许玩家显式重提合法草稿。
- 恢复入口：截止只禁止新提交和重试，不阻断在线查询原 requestId；任务消失后旧窗口的 sending/unknown/pending 与终态摘要继续显示，但不会向新窗口重发。

## 3. 响应式布局与断点

采用“一份组件、一份草稿、一份座位 DOM”的设计，支持桌面、平板、横屏手机与竖屏手机：

1. **宽屏环形模式**（`>1180px` 且座位数 `<=13` 且空间充足）：
   - `StageActionCard` 居于舞台中央保留区（`position: absolute; left: 50%; top: 52%; transform: translate(-50%, -50%); width: min(480px, 55%);`）；
   - 座位沿外环以绝对坐标排布。
   - 每次候选 ring 都使用同一视觉坐标系测量卡片、座位主块、工具和角标；8 CSS px 间距按实际 zoom 换算。若卡片越界或发生交叠，本周期锁定 flow，直到任务、座位组成、舞台宽度或可见性发生外部变化后重新测量候选 ring。
   - 候选 ring 的复核必须在 ring 几何真正渲染后同步进行（提交后的 `useLayoutEffect`，paint 前完成），不得依赖 ResizeObserver/rAF 的时序：在 flow 位置测量卡片必然判为不通过，是加宽后恢复滞后的根因。
2. **非环形模式**（大人数、窄屏、手机端）：
   - 团队方案、指定发言顺序与只读观察采用正常文档流，避免较高内容遮挡环形座位和次数加减工具；
   - 统一采用“**行动卡在舞台顶部正常文档流，完整座位网格紧随其后**”；
   - `681px–1180px`：`.stage-seats--ring` 与 `.stage-seats--grid` 统一使用 4 列网格（`repeat(4, minmax(0, 1fr))`），清除环形座位的绝对定位和固定高度；
   - `<=680px`（包含 390×844 竖屏手机）：统一使用 3 列网格（`repeat(3, minmax(0, 1fr))`）；
   - 移动端行动卡优先使用自然文档流，页面自然纵向滚动，软键盘呼出时不遮挡公屏输入框与发送按钮。
